Where: Docker Desktop 28.1.1 on a laptop (Node 22.21 image `node:22-alpine`, Postgres 16, Redis 7 with `noeviction` + AOF, Mailpit). ## What had to change before it ran (all of it belongs in the article)

| Found | Fix | Article use |
|---|---|---|
| `bullmq@6.4.2` no longer depends on `ioredis`; the Worker threw "BullMQ could not load the optional 'ioredis' package" at boot. `ioredis` and `redis` are optional peers (`>=5.0.0`); `pg` is also a peer. | `npm install ioredis@5` (5.11.1; 6.0.0 is a brand-new major) and pass a client: `new Redis({ host, port, maxRetriesPerRequest: null })` (named export `Redis` under NodeNext). | Prerequisites: one sentence, because every v6 reader hits it. |
| A `UPDATE … SET amount = amount + $1 * $2` with two untyped parameters failed in Postgres: `operator is not unique: unknown * unknown`. Every deposit and withdrawal job failed five times. | `($1::int * $2::numeric)`. | The first FAILED incidents in the project were a real bug Drumbeats caught 100 ms after the first failure ping, before I had looked at a log. Keep it. |
| `payload` sent as a JSON object was stored as `null`. Drumbeats keeps `payload` only when it is a string. | `JSON.stringify` the payload object in the adapter. | One sentence next to the adapter. |
| `min_duration_seconds: 1` on `balance-check` flagged every run as `TOO_FAST`: the real check takes 20–150 ms. | Cleared it (`update_monitor` with `null`) and resolved the DURATION_LOW incident. | Drop drill (f). Minimum duration is for jobs measured in seconds; say so. |
| `docker compose build api` only rebuilt the `api` image; `worker` and `relay` kept a stale image although all three use `build: .`. | One `image: tulip-jobs` shared by the three services. | Not article material. |

## Flows verified

Deposit (EUR 250, bank reference) → `202` in the request → outbox row → relay → `deposit-fiat-confirm` → ledger credited, wallet updated → outbox `email-transaction` → relay → Mailpit. Withdrawal (0.1 BTC) → reserve → `withdrawal-crypto` (3 s stub) → settled → email. Ledger and wallet agree after every settlement (`SELECT asset, SUM(available+reserved)` equals `wallet_balances.amount`). The minutely balance check ran every tick with `run_id = repeat:balance-check-minutely:<epoch ms>` and 20–150 ms durations. Relay heartbeat landed every 30 s (21:12:06, 21:12:37, 21:13:07, …).

## Found after the drills: pings can arrive out of order

`deposit-fiat-confirm`, run `374a6a16-…` (the drill-D deposit, 21:23:52): the SUCCESS ping was recorded at 21:23:52.807 and the START ping at 21:23:52.813. The job took 20 ms; both pings were fire-and-forget `fetch` calls and the second one won the race. Drumbeats then had a START with no finish after it and, 120 s later (21:26:00.119), closed the run as FAILED with `Timeout: run exceeded max_duration_seconds (120s)`, opening a FAILED incident on a job that had succeeded.

Adapter fix (now in `src/drumbeats.ts`, 42 lines): keep a promise per job id and queue each job's pings behind the previous one, so start is on the wire before success or failure. Verified with a fresh deposit at 21:29:13 (START then SUCCESS in order; incident resolved). Article: one sentence in the adapter section, because every sub-50 ms job hits this.
